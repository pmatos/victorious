# Speech is decoded sequentially with the previous text as context

The product decoded every stretch of speech through faster-whisper's `BatchedInferencePipeline` with `condition_on_previous_text=False`, so each 30 s chunk was decoded without the text before it. With `large-v3-turbo` (ADR 0005) that produced long Transcript segments that were all lowercase with no punctuation, and sometimes lost the end of a sentence (issue #75: "i was like no i didn't want to get your car just to register you you're when you're 18 yeah yeah"). whisper.cpp decodes sequentially and conditions on the previous text, which is what gives it punctuated, coherent text. Batched decoding cannot do that, because the chunks are decoded at the same time.

Decision: `_transcribe_window` calls `WhisperModel.transcribe` once per candidate language with `clip_timestamps` set to the VAD stretches (`vad_filter=False`, the product's own VAD, music masks and grouping are unchanged), `condition_on_previous_text=True` and the library's default temperature fallback. The language choice (`candidate_languages`, `pick_reading`), `is_speech`, `drop_repeated` and the confidence fields (`avg_logprob`, `no_speech_prob`, `compression_ratio` are on sequential segments too) are unchanged. Matches are still decoded one after another and the speech stage does not use `--jobs`, so the output does not depend on it.

Numbers. Five 300 s windows of the 2026-10-09_11-59-53 Recording (the windows of ADR 0005, with the product's music masks), turbo before (batched) and after (sequential), both scored against a sequential `large-v3` with previous-text context (the reference of ADR 0005 was itself decoded batched, which flattered the old path, so it was rebuilt; 357 segments, 1740 words). Word agreement is after lowercasing and stripping punctuation.

| | batched turbo (before) | sequential turbo (after) |
|-|-|-|
| word error rate against the reference | 17.6% | 16.1% |
| reference words missing (dropped speech) | 141 of 1742 | 68 of 1742 |
| words the reference lacks | 49 | 104 |
| long (over 8 words) segments with no capital and no punctuation | 17 | 3 |
| segments with punctuation / with a capital | 89% / 90% | 98% / 97% |
| segments | 261 | 379 |
| back-to-back identical segments | 0 | 9 (the reference has 7) |
| segments removed by the loop filter | 0 | 3 |

Per window the error rate went 10.8 to 12.2% (A), 19.6 to 21.8% (B), 27.9 to 17.5% (C), 18.8 to 15.1% (D) and 17.3 to 14.6% (E): A and B got slightly worse, the other three better. Flat segments went from 3, 6, 1, 3, 4 to 0, 3, 0, 0, 0; the 3 left are the first 20 s of window B, which was cut in the middle of a conversation, so the first stretch of every window has no text before it. The extra words are mostly short interjections ("Yeah.", "Thank you.", "What?") that the sequential reading splits out and the reference sometimes omits, which is also why there are 45% more, shorter segments. On the music window C the lobby music is still read as a Portuguese "Obrigado." at 0.6 confidence (as in ADR 0005, before and after), the 47 other segments are real speech, and no loop appeared, so `is_speech` and `drop_repeated` stay as they are. The loop filter removed 3 segments, all in window B (counted over both language readings of unsure stretches, so not necessarily in the kept one); the kept output there has only pairs of identical segments inside a conversation, which the reference has too.

Cost. Paired runs of old and new on the same audio, alternating, on a machine at a load average of 30-45 over 24 logical CPUs: 1.4x the wall time and 1.4x the CPU time over six pairs (1.0x to 2.0x per pair), 1.8x when the machine was busier. Whisper alone for a 3 h Recording (about 10,400 s inside Matches) therefore goes from about 45-60 min to about 65-85 min on a quiet machine and from 1.5-2.5 h to 2-3.5 h on a loaded one. Decoding is not deterministic: the temperature fallback samples, so a rerun can differ by a few segments (83 and 84 segments, 97 and 100, on the same window), as it could with the batched path. Several Matches or windows were not decoded concurrently, because the CPU is already saturated by one decode and the gain is not worth tying the output to a pool.

Consequences. Transcripts change (more, shorter, punctuated segments) but are not part of the Observation cache, so no cache version is bumped. The segment counts in the README run-time table were measured with the batched path and are stale until the next whole-Recording run. Caveats: five windows of one Recording, the reference is itself a Whisper, and the 17.6 to 16.1% change is within what the first-stretch effect and sampling can move, so the evidence is the flat-segment, punctuation and dropped-speech figures, not the small change in word error rate. Window B's error rate rose and the first stretch of each Match window still starts without context. Issue #30 (speed) is not touched here.
